
关于“通过 user journey 发现需求与架构设计不符”的问题

这个问题可以抽象为 `需求与实现的差异` ，是任何工作中的常见现象（也是 Elfiee 力求解决的痛点）。

我们的目标：
1. 找到用于衡量`需求与实现的差异` 的 **发生率** 或 **严重程度** 的指标
2. 找到指标，用于衡量 *发现 或 解决*`需求与实现的差异` 的 **效率** 的指标
3. 找到用于衡量 **同一类差异的复发率** 的指标

用这三个指标的变化来反映 Elfiee 的价值。

## 1. 指标一：M/N 

M = 根据 PM 的 UJ 生成的 test case 数量
N = 根据 Dev 的架构设计复杂度，理论上估算的 test case 数量

### 1.1. 这个指标里包含的假设

4. 研发模型 = 现实，实现复杂度 = 业务复杂度
5. 用 PM 的user journey 生成的 test case 和 研发的 test case 是一回事  
	1. PM 的 Case 是端到端的，研发的 Case 是单元级别的
6. 所有人都用AI"一把梭"

### 1.2. 能衡量的

7. PM理解的行为覆盖多少研发行为 / 双方对同一个功能“复杂程度”的认知偏差——**适合在双方对齐实体&状态后，发现：**
	1. **PM 遗漏的功能点**
	2. **PM 忽略的异常状态**
	3. **PM 未意识到的系统复杂度**

### 1.3. 不能衡量的

8. 语义的一致性：N = 10, M = 10，但 PM 的 10 个是关于“体验优化”，研发的 10 个是关于“后端日志”。

9. 过度设计：如果 M≫N 是因为研发引入了不必要的抽象，这个指标会误导大家以为是 PM 考虑不周。

10. 解决问题的成本：发现不符之后，我们如何对齐？

## 4. 指标四：在项目不同阶段发现的（不同种类）差异数量（间接表达动态/ 返工成本

理想状态：
在项目初期就开始对齐
先对齐实体和状态机，后续再对齐M/N

| 差异种类\阶段 | 阶段一 | 阶段二 | 阶段三 | 阶段四 | ……  |
| ------- | --- | --- | --- | --- | --- |
| 实体数量差异  | 3   | 0   | 0   | 0   |     |
| 状态机差异   | 1   | 3   | 0   | 0   |     |
| M/N     | -   | -   | 50% | 90% |     |
|         |     |     |     |     |     |

而不是：
有了M和N后才开始对齐
由于M/N对不齐，再回去找状态机和实体数量差异（这样返工更多）

| 差异种类\阶段 | 阶段一 | 阶段二 | 阶段三 | 阶段四 | ……  |
| ------- | --- | --- | --- | --- | --- |
| 实体数量差异  | -   | -   | -   |     |     |
| 状态机差异   | -   | -   | -   |     |     |
| M/N     | -   | -   | 20% |     |     |
