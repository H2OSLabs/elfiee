## 详细 User Journey

### UJ-GC-001｜根集合定义与可达性判定

**场景** 系统需要确定哪些 Block 是"活跃的"（可达的），哪些已经失去所有引用。根集合是可达性分析的起点，类似于编程语言 GC 中的"根对象"。

**流程**

- 系统定义根集合：所有在 VFS 中拥有至少一条路径引用的 Block 构成根集合。
- 从根集合出发，沿 Block 的 `children` 关系链接（`implement`、`reference` 等）进行传递性遍历。
- 所有从根集合可达的 Block 标记为"可达"。
- 不在可达集合中的 Block 标记为"不可达"。

**预期结果**

- **判定精确：** 可达性分析覆盖 VFS 路径引用和关系链接两个维度，不遗漏间接引用。
- **根集合明确：** 用户可理解"一个 Block 如果没有 VFS 路径且不被任何其他 Block 引用，就是不可达的"。
- **传递保护：** 即使 Block 自身没有 VFS 路径，只要它被某个可达 Block 引用，就不会被判定为不可达。

---

### UJ-GC-002｜查看不可达 Block 列表（GC 预览）

**场景** 用户希望在执行清理前了解哪些 Block 将被影响，以避免误删仍有价值的内容。

**流程**

- 用户在 Project 管理界面选择「查看不可达 Block」。
- 系统执行可达性分析，生成不可达 Block 列表。
- 列表展示每个不可达 Block 的基本信息：`block_id`、`block_type`、最后修改时间、原 VFS 路径（如有历史记录）。
- 用户可逐个检查 Block 内容，确认其确实不再需要。

**预期结果**

- **透明可审：** 用户在清理前完整了解影响范围。
- **信息充分：** 列表提供足够信息帮助用户判断是否需要挽救特定 Block。
- **非破坏性：** 预览操作本身不修改任何状态。
