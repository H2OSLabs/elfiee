## 详细 User Journey

### UJ-EVOLVE-01｜task.commit 触发 Skill 生成流程

**场景** 一个 Task 被成功 commit 后，系统自动启动 Skill 生成流程，无需用户手动触发。

**场景流程**

- 用户或 AI Agent 完成 `task.commit`，Event Log 记录 commit 事件。

- 系统监听到 commit 事件，检查该 Task 的 Evidence 摘要：只有当 Task 具备充分的正向 Evidence 时，才启动 Skill 生成流程。

- 系统创建一个内部任务：从该 Task 的完整因果链中提炼可复用模式。

- 生成流程在后台异步执行，不阻塞用户的后续操作。

**预期结果**

- **零操作触发：** 用户完成 commit 后，Skill 生成自动发生，用户无需额外操作。

- 系统通过 Evidence 质量门槛过滤——Evidence 不充分的 Task（如只有手动确认、没有测试通过）不会触发 Skill 生成，避免低质量经验被固化。

### UJ-EVOLVE-02｜分析 Task 的执行路径

**场景** 系统需要从 Task 的完整历史中，提取出"可泛化的执行模式"，而非复制具体的实现细节。

**场景流程**

- 系统回溯 Task 的完整生命周期事件：
    - **意图层：** Task 的初始描述与目标定义。
    - **执行层：** AI Agent 调用了哪些 Capability、使用了哪些工具、按什么顺序执行。
    - **验证层：** 哪些测试被执行、Evidence 的正向/负向分布。
    - **修复层：** 是否经历过失败→修复→重试的循环，以及最终成功的关键修改。

- 系统对执行路径进行抽象化处理：将具体的文件名、变量名替换为泛化的参数占位符。

- 系统识别路径中的"决策节点"——那些可能导致不同结果的关键选择点。

**预期结果**

- **经验提炼而非复制：** 系统提取的不是"在 main.rs 第 42 行添加了 import"这样的具体操作，而是"当需要添加新依赖时，先检查 Cargo.toml 再更新代码"这样的可泛化模式。

- 修复循环被特别标注——"第一次尝试 X 失败了，改用 Y 成功了"本身就是极有价值的经验。

### UJ-EVOLVE-03｜生成 Skill 草稿

**场景** 系统将提炼的执行路径转化为一个结构化的 Skill 草稿，供后续审核和发布。

**场景流程**

- 系统生成 Skill 草稿，包含以下结构：
    - **Skill 名称与描述：** 基于 Task 描述自动生成，简明概括该 Skill 的用途。
    - **前置条件：** 执行该 Skill 前需要满足的环境或状态要求。
    - **步骤模板：** 泛化后的执行步骤序列，包含参数占位符。
    - **验证标准：** 基于原 Task 的 Evidence 类型，定义该 Skill 的成功标准。
    - **关联 Archive：** 指向产生该 Skill 的原始 Archive Block，支持溯源。

- Skill 草稿以 Block 形式存储在 `.elf` 容器中，类型标记为 `skill_draft`。

- 草稿创建事件记录在 Event Log 中，包含来源 Task ID 和 Archive ID。

**预期结果**

- **结构化而非散文化：** Skill 草稿不是一段自由文本的"经验总结"，而是具有明确结构的可执行模板。

- 每个 Skill 草稿都有"血统"——可以追溯到产生它的那个具体 Task 和 Archive。
