## 详细 User Journey

### UJ-TT-001｜查看某个历史事件点的状态快照

**场景**
用户希望了解 Project 在某个过去时刻的完整状态 — 当时有哪些 Block、内容是什么、Block 之间的关系如何。这是一次 **只读** 操作，不会对当前状态产生任何影响。

**流程**

- 用户在 Timeline UI 中浏览事件列表，选择一个感兴趣的历史事件节点。
- 系统通过 `get_state_at_event` 从 `_eventstore.db` 重放事件到该节点，构建该时刻的完整状态快照。
- 系统以只读模式展示该快照：Block 列表、Block 内容、关系图、权限配置等，均反映选定时刻的状态。
- 用户可以自由浏览快照中的任意 Block，但无法在此模式下编辑。

**预期结果**

- **完整还原：** 历史快照包含选定时刻的全部状态信息，不仅是文本内容，还包括 Block 关系、Editor 权限、Task 状态等。
- **当前状态不受影响：** 查看历史快照是纯粹的只读操作，关闭快照视图后，用户回到最新状态。
- **任意时间点可达：** 只要事件存在于 `_eventstore.db` 中，用户就可以查看对应时刻的状态。

### UJ-TT-002｜Restore 到历史版本

**场景**
用户确认某个历史版本的内容更为理想（例如最近的修改引入了错误，或 AI Agent 的某次重写偏离了方向），决定将状态恢复到那个历史版本。Restore 的核心语义是 **基于历史状态创建新事件**，而非删除或覆盖已有事件。

**流程**

- 用户在历史快照预览中（UJ-TT-001）确认目标版本，发起 Restore 操作。
- 系统读取目标历史快照中的状态，生成一组新的事件，将当前状态更新为历史快照中的内容。
- 新事件被追加到 `_eventstore.db`，事件的 Attribute 记录了执行 Restore 的 Editor 身份，Value 中包含恢复后的内容。
- State Projector 将新事件投影到内存状态，用户看到的当前视图更新为历史版本的内容。
- 原有的事件日志 **完整保留**，包括被 Restore "覆盖"的那些中间版本。

**预期结果**

- **事件日志不可变：** Restore 不删除、不修改任何已有事件。事件日志始终只追加。
- **Restore 本身被记录：** Restore 操作作为新事件被记录，包含"谁在什么时间基于哪个历史版本执行了 Restore"的完整信息。
- **可逆性：** 由于 Restore 是创建新事件，如果 Restore 后发现不理想，可以再次 Restore 到更早或更晚的版本 — Restore 的 Restore 同样被完整记录。
- **归因清晰：** Restore 事件的 Attribute 格式为 `{editor_id}/{cap_id}`，明确记录是谁执行了恢复操作。

### UJ-TT-003｜对比当前状态与历史状态

**场景**
用户在决定是否 Restore 之前，希望先了解当前状态与某个历史版本之间的具体差异。差异对比帮助用户做出更有信心的决策，而不是盲目地恢复。

**流程**

- 用户在 Timeline UI 中选择一个历史事件节点，选择"与当前状态对比"。
- 系统同时持有两份状态：当前状态（State Projector 的最新投影）和历史快照（`get_state_at_event` 的结果）。
- 系统以 diff 视图呈现两份状态之间的差异，包括：
    - Block 内容变化（文本增删改）
    - Block 结构变化（新增、删除、移动的 Block）
    - 关系变化（新增或断开的 `children` 关系）
- 用户可以逐项审查差异，决定是否执行 Restore。

**预期结果**

- **差异可视化：** 用户无需在脑中拼接记忆，系统直接呈现精确差异。
- **决策辅助：** 对比视图帮助用户判断历史版本是否真的"更好"，而不是凭直觉恢复。
- **粒度清晰：** 差异以 Block 为单位展示，用户可以快速定位关键变化点。

### UJ-TT-004｜对单个 Block 进行时间旅行

**场景**
用户只关心某个特定 Block 的历史演变，而不是整个 Project 的状态。例如，某段 Markdown 文档被反复修改，用户想回溯某一版本的措辞；或者某段代码在某次修改后出现了 bug，用户想查看修改前的版本。

**流程**

- 用户在某个 Block 上触发"查看历史"操作。
- 系统从 `_eventstore.db` 中筛选出与该 Block（`block_id`）相关的所有事件，按 Vector Clock 排序展示。
- 用户在 Block 的专属 Timeline 中浏览各版本，选择某个版本查看快照。
- 若用户决定恢复该 Block 到某个历史版本，系统仅对该 Block 创建新的写入事件，其他 Block 的状态不受影响。

**预期结果**

- **精确粒度：** 时间旅行的范围限定在单个 Block，减少信息噪声。
- **独立 Restore：** 恢复单个 Block 不影响 Project 中其他 Block 的当前状态。
- **完整历史链：** 该 Block 的所有版本均可追溯，包括创建、每次修改、以及任何 Restore 操作。

### UJ-TT-005｜基于历史快照理解演变轨迹

**场景**
用户或 AI Agent 需要理解 Project 或某个 Block 的演变过程 — 不是查看某个时间点的快照，而是理解"从 A 状态如何一步步变为 B 状态"。这在复盘、审计、以及 AI 学习历史经验时尤为重要。

**流程**

- 用户选定一个时间范围（起始事件 → 结束事件），请求查看该区间内的演变轨迹。
- 系统按序展示该区间内的关键事件：每个事件的 Editor 归因、操作类型、影响的 Block、具体的内容变更。
- 用户可以逐步"播放"事件序列，观察状态如何从起始状态演变为结束状态。
- AI Agent 可以读取演变轨迹，理解决策路径，为后续任务提供上下文参考。

**预期结果**

- **过程可见：** 不仅知道"变成了什么"，更知道"怎么变的"和"谁在什么时候做了什么"。
- **决策路径可追溯：** 每一步变更都有明确的 Editor 归因和时间戳，形成完整的因果链。
- **AI 可消费：** 演变轨迹作为结构化的历史数据，可以被 AI Agent 用于学习和参考。
