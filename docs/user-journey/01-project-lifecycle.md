## 1   Journey 1：创建与初始化 Project

  

**UJ-PROJ-001：创建或打开 Project 作为工作上下文**

  

**场景**

产品准备开始一次新的工作或实验。

  

**场景流程**

- 创建或打开一个 Project

- 初始化 Project 内部的事件记录与状态恢复机制

- Project 进入可工作的 active 状态

  

**预期结果**

- Project 在 Project Library 中可见

- Project 拥有稳定的唯一标识

- 后续所有 Task、Block、Session 均归属该 Project

  

---

  

## 2   Journey 2：准备执行环境

  

**UJ-PROJ-002：为 Project 准备可执行环境**

  

**场景**

Dev 需要在 Project 中引入真实代码环境，并让 AI Agent 具备参与能力。

  

**场景流程**

- 将外部代码仓库引入 Project 作为工作目录

- 在 Project 中创建并启用 Agent 与 Skill

- 重启或刷新外部 AI 编程环境，使其与当前 Project 建立连接

  

**预期结果**

- Project 具备可读写的代码上下文

- Agent 能够在 Project 范围内工作

- 后续 Task 可被 Agent 与人类共同执行

  

---

  

## 3   Journey 3：定义 Task

  

**UJ-PROJ-003：在 Project 中定义一个可执行 Task**

  

**场景**

PM 或 Dev 希望明确一次工作的目标、约束与验收条件。

  

**场景流程**

- 在 Project 中创建一个新的 Task

- 填写任务目标、约束条件与验收标准

- 为 Task 指定明确的 Task Type

- （可选）引用历史 Task 或 Skill 作为参考上下文

  

**预期结果**

- Task 成为 Project 中的一个一等对象

- Task Type 可作为后续实验分组与对比依据

- Task 在未执行前处于可理解、可复用的定义状态

  

---

  

## 4   Journey 4：执行 Task

  

**UJ-PROJ-004：围绕 Task 进行人机协作执行**

  

**场景**

Dev 与 Agent 围绕一个 Task 展开实际工作。

  

**场景流程**

- Dev在 AI 编程环境中开始该 Task

- 代码被逐步编写或修改

- Task 与具体代码实现建立明确关联

- Dev与 Agent 发生多轮对话与澄清

- Dev运行测试或编译以验证结果

- 系统持续记录执行过程中的关键验证结果

- 执行过程中，Dev确认或修订 AI 生成的阶段性总结

  

**预期结果**

- Task 与执行 Session 建立稳定绑定关系

- 代码演进过程具备可追溯性

- 澄清、返工、验证等行为被自然沉淀为历史记录

- Task 逐步逼近可提交状态

  

---

  

## 5   Journey 5：提交 Task 结果

  

**UJ-PROJ-005：提交 Task 并固化结果**

  

**场景**

Dev 认为 Task 已完成，需要将结果固定为一个可信版本。

  

**场景流程**

- Dev发起 Task 提交

- Project 导出当前相关文件状态

- 生成一次稳定的提交记录

- Task 状态从执行中转为已完成

- PM 或相关角色进行验收验证

  

**预期结果**

- Task 对应的成果被稳定固化

- 提交结果可被外部复现与验证

- Task 的执行周期形成明确边界

  

---

## 6   Journey 6：PM 验证 Task 结果


**UJ-PROJ-006：PM 验证已提交的 Task 结果**

**场景**  
开发者已认为 Task 完成并提交结果，但该结果是否满足最初定义的需求、约束与验收标准，仍需由 PM 进行验证确认。

**场景流程**

- PM 打开已提交状态的 Task
    
- PM 阅读 Task 的原始定义（目标、约束、验收标准）
    
- PM 查看与 Task 关联的最终实现结果与验证信息
    
- PM 运行或复查验收验证（如拉取代码、运行脚本、检查输出）
    
- PM 判断 Task 是否满足验收条件，并给出明确结论：
    
    - 验证通过
        
    - 验证未通过（需修正）
        

**预期结果**

- Task 的“是否完成”不再仅由开发者单方判定
    
- Task 的完成状态具备明确的验收语义
    
- 验证结论成为 Task 生命周期中的一个独立节点
    
- 若验证未通过：
    
    - Task 可回到可执行状态
        
    - 原提交结果仍被保留为一次历史尝试
        
- 若验证通过：
    
    - Task 具备进入归档阶段的前提条件
        

### 6.1   Task 被明确否定（Rejected）

**UJ-PROJ-006-A：PM 否定已提交的 Task 结果**

**场景**  
PM 认为当前 Task 的实现路径或结果不满足验收标准，或在方向、约束理解上存在根本性问题。

**场景流程**

- PM 标记 Task 为「未通过验证」
    
- PM 给出否定理由（如：遗漏关键约束 / 方向性错误 / 不符合业务预期）
    
- Task 不回到执行中，而进入一个明确的被否定状态
    

**预期结果**

- Task 进入一个稳定的 Rejected / Needs-Fix 状态
    
- 本次提交被视为一次**完整但被否定的尝试**
    
- 否定原因与对应实现路径被保留
    
- 该失败结果可在未来被检索、引用与分析
    
- AI 可学习到「哪些路径已经被明确否定过」
    

---

### 6.2   基于被否定经验重新执行 Task

**UJ-PROJ-006-B：基于否定经验重新发起 Task 执行**

**场景**  
团队决定在已有失败经验的基础上，重新尝试同一 Task Type 的问题。

**场景流程**

- 新一轮 Task 执行开始
    
- 执行前可访问历史被否定的 Task 及其否定原因
    
- 开发者与 AI 在执行过程中主动规避已被否定的路径
    

**预期结果**

- 新 Task 与被否定 Task 之间形成清晰的对照关系
    
- Second-use 中避免重复走入已知错误路径
    
- 失败经验成为真实可用的学习资产

## 7   Journey 7：归档完成的 Task
  

**UJ-PROJ-007：归档 Task 以供未来复用**

  

**场景**

Task 已完成，且其过程与结果具备长期价值。

  

**场景流程**

- Dev 对 Task 发起归档

- 系统生成 Task 的归档文档

- 归档内容汇总 Task 定义、实现、验证与关联关系

- Task 状态转为 Archived

  

**预期结果**

- Task 成为 Project 的长期知识资产

- 归档内容可在未来被检索与引用

- Task 可作为 Second-use 的学习输入

  

---

## 8   Journey 8：归档被否定的 Task

**UJ-PROJ-008：将被否定的 Task 归档为失败经验资产**

**场景**  
Task 已被 PM 明确否定，其实现路径或决策结论被证明不可取，但该失败过程本身具有重要的学习与复用价值。

**场景流程**

- 团队决定不再继续修复当前 Task 版本
    
- 对该 Task 发起归档操作
    
- 系统生成一份「失败归档记录」，完整保留：
    
    - Task 的原始目标与约束
        
    - 实际采用的实现路径
        
    - PM 的否定结论与理由
        
    - 关键失败节点与误判点
        
- 该 Task 不再进入执行状态
    

**预期结果**

- 被否定的 Task 进入稳定的 Archived（Rejected）状态
    
- 失败被视为一次**完整且已关闭的决策尝试**
    
- 失败原因成为显式、可检索的知识资产
    
- Task 不会再被误认为“未完成”或“中断状态”

## 9   Journey 9：引用失败归档

**UJ-PROJ-009：Second-use 中显式引用失败经验**

**场景**  
团队在同一 Task Type 上再次尝试问题，希望避免重复已知错误。

**场景流程**

- 新 Task 在定义或执行前访问历史归档
    
- 失败归档被作为参考上下文呈现
    
- 执行过程中，人类或 AI 主动规避已被否定的路径
    
- 若新路径仍接近历史失败点，可被及时识别与纠偏
    

**预期结果**

- Second-use 明确区别于 First-use
    
- 执行效率与准确度因“错误规避”而提升
    
- AI 学到的不只是“怎么做”，而是：
    
    - **哪些不能再做**
        
    - **为什么不能做**
        

--- 
## 10   Journey 10：引用成功归档

**UJ-PROJ-010：Second-use 中显式引用成功归档**

**场景**  
团队在同一 Task Type 上再次执行任务，希望复用已经被验证正确的解决路径，而不是从零开始探索。

**场景流程**

- 新 Task 在定义或执行前访问 Project 中的历史归档
    
- 系统呈现与当前 Task Type 匹配的成功归档
    
- 成功归档作为参考上下文被引入，包括：
    
    - 已验证有效的目标拆解方式
        
    - 关键约束的处理策略
        
    - 成功实现所采用的整体路径
        
- 执行过程中，人类或 AI 主动沿用或改写这些成功路径
    

**预期结果**

- Second-use 明确复用了 First-use 的成功经验
    
- 执行过程减少不必要的探索与澄清
    
- 成功路径被再次验证或轻量调整
    
- 成功经验的稳定性得到增强
