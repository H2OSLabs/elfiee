## 4. 详细 User Journey

### UJ-HITL-01｜查看 Skill 草稿审核队列

**场景** 用户需要了解系统自动生成了哪些 Skill 草稿，以便安排审核时间。

**场景流程**

- UI 中的审核面板（或通知标记）显示待审核的 Skill 草稿数量。

- 用户打开审核队列，看到所有状态为 `pending_review` 的 Skill 草稿列表。

- 列表中每个草稿显示：草稿名称、生成时间、来源 Task 名称、建议类型（新建/更新）。

- 草稿按生成时间倒序排列，最新的排在前面。

**预期结果**

- **一目了然的审核负担：** 用户可以快速评估审核工作量，决定是立即审核还是稍后处理。

- 审核不是强制的紧急任务——草稿在队列中等待，不影响系统正常运行。

---

### UJ-HITL-02｜审阅 Skill 草稿详情

**场景** 用户选择一个草稿进入详情页，需要理解这个 Skill 是什么、从哪来、是否合理。

**场景流程**

- 用户点击草稿进入详情视图，看到完整的 Skill 草稿内容：
    - **Skill 名称与描述：** 该 Skill 做什么。
    - **步骤模板：** 泛化后的执行步骤。
    - **前置条件与验证标准：** 适用场景和成功定义。

- 详情页同时展示草稿的"血统信息"：
    - 来源 Task 的名称与链接（可跳转查看原始 Task）。
    - 来源 Archive 的摘要（可跳转查看完整 Archive）。
    - 关联的 Evidence 摘要（如：基于 5 个测试通过的结果提炼）。

- 如果是"更新建议"类型，详情页展示 diff 视图：当前已发布 Skill 与草稿建议的差异。

**预期结果**

- **可溯源的判断依据：** 用户不仅看到"草稿说了什么"，还能追溯到"草稿为什么这样说"——因为有具体的 Task、Evidence、Archive 作为支撑。

- diff 视图让"更新建议"的审核变得直观——用户只需关注变化的部分，而非重新阅读整个 Skill。

---

### UJ-HITL-03｜编辑/修改 Skill 草稿

**场景** 用户认为草稿方向正确但细节需要调整，需要在发布前进行编辑。

**场景流程**

- 用户在草稿详情页切换到编辑模式。

- 用户可以修改草稿的任何部分：名称、描述、步骤模板、前置条件、验证标准。

- 常见的编辑操作包括：
    - 修正过度泛化的步骤（将其限定到更具体的场景）。
    - 补充系统遗漏的前置条件。
    - 调整验证标准的严格程度。
    - 改进名称和描述的表达清晰度。

- 编辑操作通过 Event Sourcing 记录，保留草稿的修改历史。

**预期结果**

- **人机共创：** Skill 不是纯机器生成，也不是纯人工编写，而是"机器提炼 + 人工精修"的共创产物。

- 编辑历史被完整保留，用户可以回溯"我改了什么"以及"为什么改"。

---

### UJ-HITL-04｜发布 Skill 或拒绝草稿

**场景** 审核完成后，用户做出最终决策：将 Skill 发布到生产库，或拒绝草稿。

**场景流程**

- **发布 Skill：**
    - 用户确认草稿内容满意后，点击"发布"。
    - 如果是"新建"类型：系统在 Skill 库中创建新 Skill，并同步更新 SKILL.md。
    - 如果是"更新"类型：系统更新已有 Skill 的内容，创建新版本，旧版本保留供回滚。
    - Skill 状态变更为 `published`，可被 Pattern Matcher 检索和 AI Agent 使用。

- **拒绝草稿：**
    - 用户认为草稿质量不足或方向错误，点击"拒绝"。
    - 系统可选地要求用户填写拒绝理由（作为未来 Skill 生成的反馈信号）。
    - 草稿状态变更为 `rejected`，不进入 Skill 库。

- 无论发布还是拒绝，决策事件都记录在 Event Log 中。

**预期结果**

- **明确的质量关口：** 只有通过人工审核的 Skill 才会进入生产库，确保 AI 学到的都是"人类认可的经验"。

- 拒绝理由为 Auto Skill Generator 提供了反馈——未来可以据此改进草稿生成质量。
