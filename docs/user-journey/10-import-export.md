

> **格式约定：** 本文档描述 Elfiee 中外部文件系统与 `.elf` 容器之间的导入/导出/同步边界的完整 User Journey。
> 仅描述 **用户视角 / 系统行为 / 数据流向 / 同步语义**，不涉及 API 与实现细节。

---

## 1. Import/Export 的产品定义

在 Elfiee 中，Import/Export 是 `.elf` 容器与外部文件系统之间的桥梁。Import 将外部目录或文件转化为 Block，使其纳入事件溯源体系；Export 则将 Block 内容写回文件系统，供外部工具（Git、IDE、CI）消费。同步边界定义了哪些变更会在两侧传播、哪些不会。

## 2. Import/Export 在整体闭环中的位置

```
外部文件系统（Git Repo / 本地目录）
 ↓  Import
.elf 容器（Block + Event + VFS）
 ↓  编辑 / 协作 / 事件溯源
Block 状态演进
 ↓  Export
外部文件系统（Git Commit / 文件输出）
 ↓
CI / Review / 交付
```

如果没有 Import/Export：
- Elfiee 成为封闭系统，无法与现有开发工作流集成
- 用户无法将已有代码纳入事件溯源管理
- Task 的成果无法被外部工具验证与交付

## 4. 详细 User Journey

### UJ-IO-001｜导入外部目录为 Block 集合

**场景** 开发者准备在 Elfiee 中对一个现有 Git 仓库展开工作。需要将仓库的目录结构和文件内容完整导入到 `.elf` 容器中，使其受事件溯源管理。

**流程**

- 用户在 Elfiee 中选择「导入目录」，指定外部目录路径。
- 系统递归扫描目录结构，为每个文件创建对应的 Block（根据文件类型分配 `block_type`：`.md` -> markdown, `.py`/`.rs`/`.ts` -> code 等）。
- 系统在 VFS 中重建与原始目录一致的路径层级，每个 Block 通过 VFS 路径可达。
- 所有导入操作作为 Event 写入 `_eventstore.db`，记录导入来源与时间。

**预期结果**

- **结构保真：** 原始目录结构在 VFS 中被完整还原，用户可按原有路径导航。
- **事件可溯：** 每个 Block 的创建均有对应的导入事件，可追溯到外部来源。
- **独立演进：** 导入完成后，Block 与外部文件解耦，可在 `.elf` 内独立编辑和版本管理。

---

### UJ-IO-002｜导入单个文件为 Block

**场景** 用户在工作过程中需要将外部的某个配置文件或参考文档引入当前 Project，而非导入整个目录。

**流程**

- 用户选择「导入文件」，指定文件路径和目标 VFS 位置。
- 系统读取文件内容，创建对应类型的 Block。
- Block 被挂载到用户指定的 VFS 路径下。
- 导入事件记录文件来源路径、文件哈希和导入时间。

**预期结果**

- **精准引入：** 单文件导入不影响现有 Block 结构。
- **来源标记：** Block 的导入事件保留了原始文件路径，便于后续追溯。
- **即可编辑：** 导入完成后，Block 立即进入可编辑状态，与手动创建的 Block 无异。

---

### UJ-IO-003｜导出 Block 内容到文件系统

**场景** Task 完成后，开发者需要将 Block 中的代码或文档写回文件系统，以便进行 Git 提交、CI 验证或交付给外部团队。

**流程**

- 用户选择目标 Block 或 VFS 子树，指定导出的文件系统目标路径。
- 系统将 Block 的当前状态（State Projection）写出为对应格式的文件。
- VFS 路径层级被还原为文件系统目录结构。
- 导出操作作为 Event 记录，标注导出时间和目标路径。

**预期结果**

- **状态快照：** 导出的文件反映 Block 在导出时刻的最新状态。
- **格式兼容：** 输出文件可被外部工具（Git、编辑器、CI）直接消费。
- **可重复执行：** 同一 Block 可多次导出，每次导出均基于当前最新状态。

---

### UJ-IO-004｜理解同步边界与数据流向

**场景** 用户需要明确 `.elf` 内部编辑与外部文件系统之间的关系——哪些变更会传播、哪些不会——以避免数据一致性误解。

**流程**

- 导入后，外部文件的后续修改**不会**自动同步到 `.elf` 内部的 Block。
- 导出后，`.elf` 内部 Block 的后续编辑**不会**自动同步到已导出的文件。
- 若用户需要重新同步，必须显式执行「重新导入」或「重新导出」操作。
- 系统在导入/导出时可提示冲突：若 Block 已有内容而外部文件也有变更，用户需选择保留策略。

**预期结果**

- **边界清晰：** 用户理解 `.elf` 是独立的事件溯源空间，不是外部文件系统的镜像。
- **无隐式同步：** 系统不会在用户不知情的情况下覆盖任何一侧的数据。
- **冲突可控：** 当两侧均有变更时，用户可明确选择如何处理。

---

### UJ-IO-005｜批量导入大型代码仓库

**场景** 用户需要将一个包含数百甚至数千文件的大型代码仓库导入 Elfiee，要求导入过程高效且可控。

**流程**

- 用户选择「导入目录」并指定大型仓库路径。
- 系统提供导入预览：展示将创建的 Block 数量、目录层级、预估耗时。
- 用户可配置过滤规则（如忽略 `node_modules/`、`.git/`、`target/` 等目录）。
- 系统分批创建 Block，导入过程中显示进度，支持中断与恢复。
- 所有 Block 创建事件批量写入 `_eventstore.db`。

**预期结果**

- **可控预览：** 用户在导入前了解将发生什么，避免意外导入不需要的文件。
- **过滤灵活：** 常见的构建产物和依赖目录可被排除。
- **过程可靠：** 大批量导入不会因中途失败而导致部分状态不一致。
